Your voice agents hear and speak.

You already deploy the ears (Nova-3 / Flux STT) and the mouth (Aura / Flux TTS, Voice Agent API). Webfuse adds the missing half of the body: a live, shared browser session the agent can see and drive — on any website, with zero integration from the site, while the customer watches every move.

The body in the browser

What your agents are missing.

Eyes Page perception

Hands Session control

What Webfuse actually is

A shared browser, not a headless one

The difference that changes the product: the customer is inside the session with the agent. Not watching a screencast, not trusting a black box — co-browsing.

One live browser session

A virtual browser in the cloud. The customer joins from any device; everyone in the session sees and can control the same pages.

Works on any website

No SDK, no partner integration, no site changes. If it loads in a browser, the agent can see it and use it — logins, carts, docs, internal tools.

Automation built in

A per-session MCP server and an extension API (browser.webfuseSession) expose navigate, click, type and page perception to any agent.

The contract, for FDEs

Everything you need to wire it yourself

If you can open a WebSocket, you already know most of this. The Deepgram half is your home turf; the Webfuse half is three API calls.

1 · Connect — browser auth via subprotocol (no headers needed)
// browsers can't set Authorization headers on a WebSocket; Deepgram's
// subprotocol trick rides the credential instead. Grants work here too.
const ws = new WebSocket(
  "wss://agent.deepgram.com/v1/agent/converse",  // ← converse. /v1/agent 404s
  ["token", credential]
);
2 · Configure — one Settings message after Welcome
{
  "type": "Settings",
  "audio": { "input":  { "encoding": "linear16", "sample_rate": 16000 },
              "output": { "encoding": "linear16", "sample_rate": 24000, "container": "none" } },
  "agent": {
    "listen": { "provider": { "type": "deepgram", "model": "nova-3", "keyterms": ["Webfuse"] } },
    "think":  { "provider": { "type": "open_ai", "model": "gpt-4o-mini" },  // managed — no OpenAI key
              "prompt": "…never claim you cannot browse…",
              "functions": [ { "name": "navigate_to_website", "parameters": { "url": "string" } } ] },
    "speak":  { "provider": { "type": "deepgram", "model": "aura-2-thalia-en" } }
  }
}
3 · Act — bridge Deepgram's function calls to the Webfuse session
// Deepgram sends this when the LLM decides to act:
{ "type": "FunctionCallRequest", "functions": [{
    "id": "fc_…", "name": "navigate_to_website",
    "arguments": "{\"url\":\"google.com\"}", "client_side": true }] }

// your code (inside a Webfuse extension) — the hands:
const r = await browser.webfuseSession.relocate(url);   // shared tab navigates, live

// …then answer the agent so it can speak the result:
ws.send(JSON.stringify({ "type": "FunctionCallResponse", "id": fn.id,
  "name": "navigate_to_website", "content": "{\"ok\":true,\"url\":\"…\"}" }));
Gotchas we hit so you don't have to
GotchaWhat happens / the fix
Wrong endpointThe agent lives at /v1/agent/converse on agent.deepgram.com — not /v1/agent, not api.deepgram.com. Both of those fail the WS handshake.
Browser authNo WS headers in browsers. Subprotocol ["token", credential] works on both /v1/listen and the converse endpoint.
Deepgram-hosted LLMthink-fast is Early Access (contract customers). Managed open_ai / gpt-4o-mini needs no key of yours and works today.
Two sample ratesMic in at 16 kHz, agent speech out at 24 kHz — one AudioContext has one rate, so playback needs its own.
Silence handlingThe socket wants continuous binary frames; KeepAlive alone doesn't finalize a turn (CLIENT_MESSAGE_TIMEOUT). A live mic is fine; test harnesses must keep sending (even silence).
Scheme-less URLsLLMs happily send "url": "google.com" — normalize before calling relocate().
The refusal tellA tool-less voice agent answers “I can't browse the web” — correct behavior, wrong product. Declare the functions; the model will use them.
Where this lands in your deployments

Voice-agent use cases that need a body

Voice commerce

“Order two of those.” The agent hears it, finds the product, fills the cart in the shared browser, and confirms aloud — the customer watches every click.

Guided support & onboarding

The agent talks the customer through a flow while doing it with them — navigating to the right settings page, pointing by acting, on the customer's real account.

High-trust automation

Form filling, claims, applications — anything sensitive: the customer sees exactly what the agent types and can barge in by voice to correct it mid-action.

The pattern is the same every time: speech in, action out, witness live. Voice agents stop being phone menus and become colleagues sitting next to the customer.
